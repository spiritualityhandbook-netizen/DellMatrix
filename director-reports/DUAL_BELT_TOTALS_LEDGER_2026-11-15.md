## 1. THE DUAL-BELT RULE (Ace ruling, 2026-11-15; accepted by both authorities)

- Plans and code run as **two separate queues in parallel**. For each
  object the plan completes first, then its code; **neither belt halts
  the other**.
- The **PLAN belt** completes when an object is developed to
  execution-ready standard: mirrored against the whole plan, placed,
  done-defined. The **CODE belt** completes when the object is built,
  merged, working, and proven on main — done, with no return trip
  unless adding or modifying something new.
- **Completing a plan does not add to the completed count.** Stages of
  one object count once, when the object closes. A task is a Grand Plan
  object scratched off the list; the daily objective is 100.
- Records-only merges never count as implemented functionality.
- The PLAN belt should reach full completion long before the code;
  once the plan is fully complete, all effort focuses on the code.

## 2. BELT CLASSES

| Class | Meaning | Completes on |
|---|---|---|
| **CODE** | Completion requires product code built, merged, proven on main. Passes the PLAN belt first (plan execution-ready), then completes on the CODE belt. | CODE belt |
| **PLAN** | The object IS a design, decision, doctrine, or plan. Completing its plan completes the object. | PLAN belt |
| **RECORDS** | The deliverable is evidence: an investigation, census, audit, verification, or publication. Completes on the PLAN belt when delivered and reviewed. **Never counts as implemented code.** | PLAN belt |

Classification method: each row classified from its register text;
verification rows whose evidence is a merged test suite count CODE;
rows whose deliverable is a report or finding count RECORDS; every
judgment call is noted on its row. Titles are the crosswalk's (some
shortened there); full text lives in the MWL and the unified edition.
