### 2.2 Row #92 / SM-08 — resumability is a convention, not a mechanism

- The completion envelope (AGENTS.md section 4) defines exactly
  the right state — 15 fields from DIRECTIVE_ID to
  NEXT_EXECUTABLE_ACTION — and directs that it be maintained.
  In practice it lives inside a ~24,000-line working state file

  compact rewrite. A checkpoint that cannot be read cannot

  index a resuming worker can verify against.

**Gap:** no writer/reader pair, no integrity check, no size
discipline, no recovery test. The row's own title concedes it:
"partially embodied in practice, not verified as an objective."

## 3. What will be built (code stage, after PLAN-CONFIRM)

### 3.1 SM-07 — `reconcile_gate` in `certification_runner.py`

A pure, offline, standard-library function
`reconcile_gate(bundle) -> verdict` added to
`director-reports/certification_runner.py`, plus a CLI mode that
reads a bundle JSON and prints the verdict. The full contract —
bundle schema, the five legs (exact-head, merge-tree, mail
freshness, post-merge, fresh-clone), and the 14 refusal codes —
is fixed in `GATE_RECONCILIATION_RECORD_2026-11-20.md`, which is
part of this plan-stage PR so the authorities confirm the
contract, not just the intention. Design laws:

- One verdict over one frozen candidate (PR + head + tree); any
  drift refuses and the gate re-runs.
- Terminal sources only; a non-terminal check is a refusal, not
  a prediction. Two sources disagreeing refuses until resolved
  from the authoritative source.
- Every red check classified (pre-existing / candidate-caused /
  unexplained) before the gate; candidate-caused and unexplained
  refuse; pre-existing reconciles only with the governing
  authorization flag set, and the classification is carried into
  the verdict record.
- Mail freshness is a leg, not a courtesy: no bundle without a
  recorded watermark reconciles; a newest ruling of HOLD /
  CORRECTION_REQUIRED / INSUFFICIENT_EVIDENCE refuses.
- Malformed input returns REFUSED; the function never raises.
- The reconciler is an instrument, not a certificate — the
  verdict states that the evidence reconciles; certification
  remains the authorities' act.

`form/regress.py` is touched at code stage only if the campaign
needs the two new suites' tally tokens registered; the suites
follow the existing auto-discovery + last-token contract, so the
expected regress.py change is zero. If a change proves necessary
it is Part 0's alone to make (this Part owns the harness).

### 3.2 SM-08 — `form/resume_checkpoint.py`

A small module with `write_checkpoint(path, state)`,
`read_checkpoint(path)`, `verify_checkpoint(state) -> [problems]`,
implementing the envelope as a mechanism:

- State = the 15 completion-envelope fields (AGENTS.md section 4)
  plus a `checksum` over the canonical serialization.
- Atomic write (temp file in the same directory + replace); no
  temp residue; a torn checkpoint is never silently trusted —
  read raises, or yields a state verify rejects.
- `verify_checkpoint` names every missing field and any checksum
  mismatch; it is the resuming worker's first act.
- `COMPLETED_PHASES` is append-only across writes to the same
  path: a write that drops a completed phase is refused.
- Unknown extra fields round-trip untouched (forward
  compatibility — the envelope will grow; the mechanism must
  not punish it).
- Compactness discipline from the section 4 lesson: the writer
  refuses a state whose canonical form exceeds a stated bound
  (proposed 16 KiB — the envelope is a recovery state, not a
  log; history belongs in packets and records), naming the
  oversized field. The bound is a plan proposal, open to the
  authorities' adjustment at PLAN-CONFIRM.

The per-goal working state files adopt the checkpoint at their
next rewrite after landing; migrating the existing ~24k-line
state file is explicitly NOT part of this Part (it is an
operational act, done by the owning lane under the mechanism,
not a code change).

## 10. Risks, limitations, non-coverage

- The reconciler consumes bundles produced by operator tooling;
  bundle *collection* (driving gh/CI/mail reads) stays a
  main-session act. A dishonestly assembled bundle reconciles —
  the instrument checks consistency and completeness of
  evidence, not the honesty of its collector. That is the same
  limit `certification_runner.py` carries today, stated rather
  than hidden.
- The checkpoint mechanism proves resumability of the
  *envelope*, not of any particular worker: a resuming worker
  must still verify the checkpoint against repository reality
  (HEAD, worktree, remote) before acting on it — the envelope
  is a recovery state, not an authority.
- GP-E25's view can only be as current as its pin; the AS_OF /
  STALE labeling is the honesty mechanism, and S3's
  revalidation is a code-stage deliverable, not a plan-stage
  claim.
- The G-09 report discharges a reporting debt. It does not
  reproduce DAF-09, does not ask the Director to change the
  19/22 standing, and does not lift the certification WITHHELD
  state.
- Plan-stage CI red (section 5) is expected; anyone reading
  this branch's checks without this plan will see two failing
  suites. The tally lines in section 4 are the explanation of
  record.
