## 2. The Docked Operator object (one role, reusable; Gemini first)

Per Edition 1 file 09, the shared operator object — specified here
in full so a build circuit inherits it whole:

| Field | Meaning |
|---|---|
| `provider / actor identity` | which AI, named (first instance: Gemini) |
| `owner` | the human authority the session belongs to (Ace) |
| `operator_session_id` | one revocable session per docking |
| `permission-grant issuer` | who granted this envelope (Ace, or the Director within Ace's scoped FI-017 authority) |
| `mode` | the FI-014 session mode in force |
| `sandbox_id` | the sandbox the operator works in (Freedom Clause: reflects the whole, affects nothing until confirmation) |
| `allowed depths / tools` | the subset of the three depths + named tools granted for THIS session |
| `objectives` | what the session is for, stated before work begins |
| `expiry` | when the envelope lapses on its own |
| `cancel / kill` | revocation, exercisable at any time, effective immediately |
| `input source generation` | the generation of program state the operator is reading (stale-read protection) |
| `proposals` | the session's proposal output (the ONLY channel out of the sandbox) |
| `tool-call receipts` | every tool call receipted (what, when, result) |
| `redaction + token limits` | FI-013 bounds: what the operator may not see; the session's spend ceiling |

**Invariants (Edition 1 file 09, carried verbatim-grade):** no

## 3. Depth 1 — Nursery operator

**Purpose:** organize / cluster / draft inside the Nursery, under
Ace-set FI-011 gates.

**Work protocol (full):**
1. The operator reads the Nursery through SEE (browse / search /
   get) inside its sandbox mirror; it sees counts as shown/total —
   never a silent subset (the C5 completeness rules bind the
   operator's view exactly as they bind a human's).
2. It may: cluster pending proposals (grouping SUGGESTIONS),
   organize via topics/tags/clusters as store metadata drafts,
   draft proposal text, flag duplicates and near-duplicates with
   evidence.
3. Every output is a **PENDING, visibly-marked suggestion** in the
   Nursery — the C5R doctrine: a docked AI organizer only proposes;
   it NEVER confirms, rejects, deletes, or lands anything.
   Confirmation stays Ace's sovereign act (or the Director's, only
   within Ace's scoped FI-017 proposal authority — and Nursery
   confirmation itself is never delegated: §1).
4. Progression: the operator's latitude grows only under the FI-011
   gates Ace set (the Psalm workflow + auto-confirm gates record) —
   gate changes are Ace's acts, recorded, never inferred from the
   operator's track record by the operator or by Uni.
5. Receipts: every suggestion carries (operator, session, source
   proposals read, rationale in plain English); the suggestion's
   disposition (confirmed / rejected / expired) is receipted back
   into the session record so the operator's judgment is itself
   auditable over time.

**Done-definition contribution:** live actual activity at this depth
— suggestions flowing, dispositions receipted — is one third of
FI-017's Edition 1 done-definition (§7).

## 4. Depth 2 — Knowledge conductor

**Purpose:** work the knowledge pipeline — STORED > ELIGIBLE >
SELECTED > ROUTABLE > USED > OBSERVED > LEARNED — with receipts, the
stages never silently collapsed.

**Work protocol (full):**
1. The conductor prepares pipeline MOVEMENT PROPOSALS: e.g., "these
   stored items meet the eligibility contract — proposed ELIGIBLE,
   evidence attached"; "these eligible items fit the current
   selection question — proposed SELECTED, ranking rationale
   attached."
2. **Hard eligibility laws precede everything the conductor
   touches:** an item failing a hard law is never proposed past it,
   and explicit user choice (including the conductor's) cannot
   bypass a hard eligibility or safety law. The conductor's ranking
   work is advisory ordering only (soft), strictly downstream of
   the hard gates.
3. The conductor never moves an item itself: each stage transition
   is a proposal decided by the pipeline's existing authorities
   (the program's eligibility machinery for hard gates; Ace/the
   Director per their seats for judgment calls).
4. OBSERVED → LEARNED is fenced absolutely: observation does not
   become learning in the conductor's hands — DuoBeta's learning
   keeps its own authorized lifecycle, and the conductor's receipts
   are observations, never training.
5. Receipts per proposal: items, stage, the contract clause relied
   on, evidence, and the deciding authority's disposition.

**Done-definition contribution:** pipeline proposals with receipts
flowing at this depth, hard-law refusals demonstrated (a proposal
that would cross a hard gate is refused by the machinery, and the
refusal is the receipt).

## 5. Depth 3 — Resident developer

**Purpose:** draft development artifacts inside program state for
checking: Mandell chains, Dell compositions, growth plans.

**Work protocol (full):**
1. The developer drafts IN THE SANDBOX: Mandell Dell-chains as
   proposals (the 2026-11-09 inside-out pattern: the docked AI
   authors chains as proposals; Ace confirms; the program executes
   and returns receipts), Dell compositions (candidate arrangements
   of existing Dells — never new Dell authorities), and growth
   plans (candidate growth sequences for the growth machinery to
   admit or refuse under its own rules).
2. Drafts are checked by Uni (repository reality: does this chain
   parse, compose, and mean what its gloss claims?) and disposed by
   the authorities. A draft the developer believes in that Uni's
   check refutes is recorded as refuted — the developer's
   confidence is not evidence.
3. **Repo code lands only through Uni** — the developer never
   touches the repository; if a draft implies a code change, the
   draft is the deliverable and Uni's circuits decide the rest.
4. Receipts: draft, checker verdict, authority disposition,
   execution receipts where a confirmed chain runs.

**Done-definition contribution:** reviewable drafts reaching Uni
with provenance, per §7.

## 6. The proposal lifecycle (all depths, one road)

`sandbox work → PENDING proposal (visibly marked, receipted) →
authority disposition (Ace sovereign for Nursery confirmation; the
Director within his scoped FI-017 proposal authority; Uni for
code-shaped drafts) → execution through the existing machinery →
receipts back to the session record.`

No side doors: a docked output that reaches canonical state by any
other path is a fence breach, and the breach — not the output — is
the incident to record.

## 7. Fences that never move (restated on the paper's face)

1. Nursery confirmation is **Ace's sovereign act**.
2. Hard eligibility / safety laws precede the operator, always;
   explicit choice cannot bypass them.
3. Repo code lands **only through Uni**.
4. DuoBeta learning keeps its own lifecycle; the operator observes,
   it does not teach.
5. The operator never confirms, rejects, deletes, or lands
   anything — it proposes.
6. One revocable envelope per session: expiry and kill are real,
   tested properties of the build, not paperwork.

- **Build shape (for the future circuit):** the operator object (§2)
  as the session record; the three depths as three independently
  selectable, permissioned scopes over that one envelope (Edition 1
  done-definition); the proposal lifecycle (§6) wired to the
  existing Nursery/Dock machinery — no new gate, no new store.
- **Failing-first specs for the build (written now):**
  - `operator_never_confirms` — drive a session whose operator
    attempts a confirmation through every surface it can reach;
    at base (no operator) FAIL by absence; build passes when every
    attempt lands as PENDING or refuses, and the audit shows zero
    operator-originated confirmations.
  - `envelope_kill_is_real` — revoke mid-session; build passes
    when the operator's next action of any kind refuses, and its
    in-flight work remains sandbox-only.
  - `hard_law_precedes_operator` — seed an item failing a hard
    eligibility law; build passes when no depth can propose it
    past the gate.
  - `depths_independently_selectable` — grant depth 1 only; build
    passes when depths 2–3 refuse for that session while depth 1
    works.
