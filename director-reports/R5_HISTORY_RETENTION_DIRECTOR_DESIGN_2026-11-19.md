## 1. Independently verified source chain
- form/open.py Program.history is a list of strings, with **history_max=24**. Program.note(action) strips text and slices **[:120]**, appends, and silently retains only the last 24. A 25th note destroys the first in memory.
- Program.note_seed(dell, term, label) builds its note from label **[:40]** and delegates to Program.note. Its Step 3b chain-sanitize redaction is **CONDITIONAL, not universal**: it applies only while the transient `_chain_sanitize_redact` flag is set (the Sanitize-chain execution window, form/open.py:358). Outside that window, note_seed labels enter history **unsanitized**, bounded only by the [:40] label cut and Program.note's [:120] cut. (Correction per Uni R5-A evidence 7011704454, directed by Director §42 delta 7012186529 — the original wording of this bullet implied note_seed always sanitizes; it does not.) This is an ADDITIONAL capture-time lossy boundary; no blanket removal of redaction or label privacy rule is authorized by this design. Capture, storage, load, macro, and display remain **separate boundaries** and must be evidenced separately; no fix at one boundary proves another.
- form/persist.py _serialize_program writes **history[-24:]** independent of Program.history_max. A user could patch the live bound and still lose older entries at save.
- form/persist_rest.py restores **[str(h)[:120] for h in hist][-24:]**, independently truncating both each old entry and the number of entries. Legacy already-lost entries cannot be reconstructed.
- Program.macro_seed(n) uses history[-n:] but then slices the entire generated seed **[:200]**; Program.replay(n) draws from history, and replay_exec executes those entries. The existing replay/macro output cap is a distinct downstream limit; removing the history ring alone will NOT prove complete replay or macro truthfulness.
- The REPL History display offers more headroom than storage (history 48 / read-only clamp). The separate action undo/redo stacks and durable outcome ledger are different objects with different authority and must not be conflated with this human-readable history.
- The pinned Limits Census R5 and wave-1 verification identify all three 24-entry cuts as a CONFIRMED silent-loss defect, while the values 24 and 120 remain UNRULED. Existing DCC-XX outcome records are observational evidence, not a replacement history by automatic implication.

## 2. Proposed owner policy (for independent challenge; NOT adopted yet)
1. **Single canonical source.** Preserve the existing owner-bound Program.history as the canonical chronological list of SAFE, already-redacted note strings. Do not create a parallel mutable 'history_full' shadow that can disagree with Program.history. In live memory and the current history JSON field, preserve all legally accepted safe entries in order. Do NOT silently evict on append, save, or load; do NOT silently apply a 120-character cut.
2. **Bound belongs to a view or to explicit refusal, never invisible destruction.** Separate the old working-display default 24 from persistence semantics. If there must be a memory/disk quota, prove its origin and evaluate a declared upper budget; above-budget actions should fail explicitly BEFORE mutation (or reject the proposed archive transaction atomically), with a truthful typed quota/retention receipt. No fabricated extra past and no 'all retained' claim if legacy generations already lost history.
3. **Privacy boundary outranks losslessness.** Preserve Step 3b sanitize_text and any other authorized sensitive-value screening, per-owner isolation, and no raw protected operands leaking into note text, saved JSON, checkpoints, logs, or errors. Do NOT naively expand note_seed's existing 40-character label to raw 1000-character secrets. Treat this label loss as a separately evidenced caller-policy question: a privacy-safe structured representation/full sanitized label may be proposed only with negative leak tests and explicit review.
4. **Failure/atomicity.** The save layer must either persist a complete validated history section or fail closed with the previous durable generation retained, without partial append, false success receipt, or malformed material silently discarded. Never delete files to make a quota check pass. A successful write followed by load must preserve order and safe bytes; retries must not duplicate history entries. Reuse existing save/checkpoint transactional boundaries rather than create a second custom writer.
5. **Legacy and independent views.** Legacy files with an already truncated 24-entry history remain readable; disclose that older entries are unavailable, do not pretend they can be recovered. History count is truthful and distinguishes available vs requested and retained vs shown; read-only history viewing may page. Replay/execute must retain authorization/safety semantics and not silently execute more than the user explicitly requested. The macro_seed 200-char bound and history-REPL 48 display cap need separate coverage and either a named follow-up or a tightly proven compatible fix, NOT hidden within this save-path circuit.
6. **Single gate per source of truth.** No manual score changes: R5 stays OPEN until merged-main proof and independent credit decision. R27 display pagination and Q-LC.1 undo/redo remain separate; the 49 Grand Plan candidate additions are UNADOPTED.

## 3. Required failing-first public evidence (before touching save logic)
At pinned current main and then the proposed change head, in an isolated, real-owner public entry path:
- Create 25/48/49/201 safe distinguishable notes and prove prior first/earliest entries disappear on old code; show which boundary (live note, save, reload) caused each drop.
- Entry payloads 119/120/121/1000 safe characters: prove first irreversible cut; repeat across a direct note writer and a sanitized note_seed writer. Keep original raw source isolated; do not store secrets in test logs.
- Save/reload roundtrip of a legitimate legacy JSON with 50 history entries and a 140-character note, including owner-binding and version compatibility. Prove old loader cuts independently; prove proposed migration never invents entries that had already disappeared.
- Use a deliberate secret with a 41[Sanitize] chain and check memory, disk/checkpoints, export, CLI output and error receipts; test malformed or foreign-owner history sections fail closed or are quarantined per existing proven owner policy.
- **Negative privacy tests, both label classes (added per Director §42 delta 7012186529):** (a) an ordinary note_seed label written OUTSIDE any Sanitize-chain window — prove what actually enters history, saved JSON, checkpoints, and replay output, given that no sanitization runs on that path today; (b) a chain-redacted label written INSIDE the Sanitize window — prove the redaction survives persistence and replay and never re-expands. Cover persistence/replay for both classes. Sensitive test payloads must never be written to test logs; assert on shapes/markers, not on raw secret bytes in output.
- **history_report shown-versus-total mismatch (explicit R5-B failing-first case, per Director §42 delta 7012186529; Uni R5-A evidence 7011704454):** form/needs.py history_report slices the history first and then prints len(hist) as the note count, conflating shown with total. Failing-first case: with more entries retained than the report window shows, the report must state shown and total as separate truthful numbers; on old code it reports the sliced length as the count.
- Fault injection: failed save, failed atomic rename, truncated write, interrupted save, second load, retry. Verify prior generation intact, no duplicate event, no silent loss and truthful failure status.
- Compare History UI requested/shown/total, replay(n), replay_exec(n), and macro_seed(n) for values >24 and >48. Explicitly classify remaining independent macro 200 / seed-label 40 limits; do not certify full replay while those are still binding.
- Test concurrency/owner isolation, size growth/back-pressure and worst-case serialization. If no documented bounded resource budget exists, report it as DESIGN VALUE OWED rather than invent a quota. Old data is never silently pruned to make a test pass.
