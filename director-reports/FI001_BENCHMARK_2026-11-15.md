- **Date:** 2026-11-15
- **Measured at main:** `04abc1ea9c1296e0605ed18b303eb9b6babfb799` (origin/main, fetched 2026-11-15)
- **Kind:** READ-ONLY measurement. No product code changed, nothing committed.
- **Rerunnable script:** `FI001_BENCHMARK_2026-11-15.py` (beside this file; run from a repo root: `python3 FI001_BENCHMARK_2026-11-15.py`)
- **Machine/context:** Python 3.12.3, x86_64, AMD EPYC 9D25 (shared VM, 4 vCPU visible). All figures are medians of 9 timed runs (`time.perf_counter_ns`), queries pre-generated with a fixed seed (90% hits / 10% misses). Correctness of all three methods was asserted equal before timing. No cherry-picking: every pattern × method × scale measured is reported below.

## VERDICT

**INDEX-NOT-JUSTIFIED-AT-CURRENT-SCALE** — and the premise is **moot for the
hot path**: by-number access, the only per-atom production access, is already
served by a keyed dict (`DELLS.get`), and the derived-index prototype does not
beat it at *any* measured scale (it is marginally *slower*: 131 ns vs 111 ns
per query at the real scale; 181 ns vs 138 ns at 9,900). The registry's only
linear scan is by-name lookup, whose absolute worst case today is ~41 µs on a
path no production caller exercises per-atom. There is no measured speed
problem for a lattice index to solve.

## 1. GROUNDING — what a lattice index would index

The canonical registry (the authority FI-001 must derive from, per Q-S1.3):

| Structure | Where | Shape | Access today |
|---|---|---|---|
| `DELLS` — the Dell registry | `form/mandell/registry.py:20` (Core I literals) merged with Core II at `registry.py:74-75` | `Dict[int, Dict[str,str]]`, **100 entries, numbers 0–99, complete** (51 Core I + 49 Core II from `form/mandell/core_ii.py:8` `_ROWS`) | **Keyed**: `get_dell(n)` is `DELLS.get(n)` (`registry.py:104-105`) |
| `NAMED` — 5 alias names | `registry.py:84-90` | `Dict[str, int]` | Keyed |
| `RESERVED_DOMAIN` — reserved addresses 100–999 | `form/mandell/address_space.py:29` | `Dict[int, Dict[str,str]]`, **49 entries** | **Keyed**: `get_reserved(n)` is `RESERVED_DOMAIN.get(n)` (`address_space.py:101-105`) |
| `lookup(name)` — by-name resolution | `registry.py:110-140` | NAMED dict check, then **linear scan** over `DELLS.items()` (`registry.py:129-131`), then a second linear scan over `RESERVED_DOMAIN` (`registry.py:134-137`) | **The registry's only list-scan access path** |

Production callers (grep-verified, non-test):

- **By number (hot path):** `get_dell(n)` — `form/mandell/chain_exec.py:80,192,297`, `executor_leaf.py:679`, `seed.py:70,233`, `translate.py:236,873`, `dell_matrix/simulate_board.py:298,393`, `operator_bridge.py:146`, `manifest_resolver.py:38,49`, and ~15 more. One call per atom executed.
- **By name:** `registry.lookup(...)` — `operator_bridge.py:150`, `query_ops.py:232` (Dell-54 Query path), `manifest.py` (via `lookup` import), `seed.py`. Per *user command / name resolution*, never per atom.
- **Neighborhood / range over the registry: NONE.** No production caller performs a range or neighborhood query over `DELLS`. Band membership is decided arithmetically — `namespace_of(n)` is comparisons only (`registry.py:93-101`), `family_of(n)` is arithmetic (`address_space.py:95-99`), and `chain_exec.py:94,168` test `51 <= n <= 99` / `0 <= n <= 50` directly. Full-registry enumeration exists only where the product is inherently all-entries (proof cards, `dell_cards.py:902`; counts, `dell_matrix/core.py:108`).
- `HarmonicLattice` (`form/dell_matrix/harmonic_lattice.py:80`) is a 3-D coordinate cell store for *ideas/units*, not for Dells; it is not a registry index and no registry caller consults it.

Architectural bound that decides the flip question: the address space is
capped by design — `ADDRESS_MAX = 999` (`registry.py:79`), core registry
complete at 100 (0–99). The registry **cannot** grow to the scales where a
scan becomes expensive without a separate ruling changing the address space
itself.

## 2. BENCHMARK RESULTS (median ns per query)

Production functions at the real scale, for reference:

| Function | ns/query |
|---|---|
| `registry.get_dell(n)` | 560 |
| `registry.lookup(str(n))` (digit path → `get_dell`) | 972 |
| `registry.lookup(name)` (scan path) | **31,263** |

Micro-probe corroboration (median of 5 × 20,000 calls): `lookup("Nova")` 896 ns (first entry), `lookup("Bind")` 4,639 ns, `lookup("Compose")` 25,314 ns (last entry), `lookup("NoSuchDell")` 40,771 ns (full DELLS + RESERVED_DOMAIN double scan). Mechanism: `lookup` recomputes `s.lower()` on **every** comparison (`registry.py:130`, `:136`) in addition to scanning — a hoisted-comparison scan of the same data costs ~2.6× less on a miss (15,449 ns). The scan's cost is real but absolutely small, and part of it is a one-line inefficiency, not a missing index.

Three methods × three patterns × four scales (prototype = dense array by number + normalized name dict + sorted-keys/bisect for bands, built inside the benchmark script only):

| Pattern / method | real-100 | synth-99 | synth-990 | synth-9,900 |
|---|---|---|---|---|
| P1 number — keyed `dict.get` | **111** | **64** | **74** | **138** |
| P1 number — list scan | 2,088 | 1,419 | 32,019 | 303,960 |
| P1 number — index (dense array) | 131 | 126 | 151 | 181 |
| P2 name — keyed (name `dict.get`) | **146** | **139** | **149** | **196** |
| P2 name — list scan (= `lookup` loop) | 8,067 | 4,800 | 83,497 | 906,940 |
| P2 name — index prototype | 295 | 190 | 207 | 240 |
| P3 band — keyed (dict filter) | 7,342 | 4,809 | 46,381 | 1,177,193 |
| P3 band — list scan (filter) | 4,013 | 3,647 | 44,637 | 995,113 |
| P3 band — index (bisect slice) | **1,611** | **1,647** | **15,463** | **379,715** |
| Index build, one-time (incl. sha256 fingerprint) | 145 µs | 78 µs | 713 µs | 19.2 ms |

Reading the numbers:

- **P1 (the hot path):** the existing dict is already the fastest method at every scale. A derived index *cannot* improve it — the prototype's dense array ties/loses because it re-implements the same O(1) access with an extra bounds check. FI-001's founding image ("put them in a lattice to pull them faster") is, for by-number retrieval, already satisfied by the registry's own dict.
- **P2 (by name):** the only genuine scan. Index/keyed access is ~30–55× faster in *ratio* at the real scale, but the absolute saving is ≤ ~31 µs per call (production `lookup` median on a mixed query set), on a path exercised per user command, not per atom. A caller doing 1,000 name resolutions in a burst would save ~31 ms — and the honest minimal fix for even that is a name→number dict (a few lines, exactly the "keyed" column), not a spatial lattice with coordinates, neighborhoods, and a persisted cache.
- **P3 (band/neighborhood):** the index wins ~2.5× at the real scale (1.6 µs vs 4.0 µs) — and **no production caller performs this query**. At 9,900 the win narrows (~2.6×) because band cost becomes output-bound (the band holds ~half the entries; returning them dominates). Speed for a query nobody runs is not capability.
- **Build cost** is trivial at registry scales (145 µs at 100 entries) — cost was never the obstacle; *absence of a problem* is.

## 3. WHERE THE ANSWER FLIPS

Scan cost grows ~linearly (~167 ns per scanned item for name scans at 9,900).
A name scan reaches ~1 ms/query only when the *average* scan depth reaches
~6,000 items — a registry of roughly **11,000+ entries**. That scale is
unreachable for the registry itself: the address space is architecturally
capped at 1,000 (`ADDRESS_MAX = 999`), at which the worst-case name scan is
bounded near ~90–180 µs and by-number access remains O(1) regardless.

The verdict flips only if the *dataset or the access pattern* changes, e.g.:

1. The indexed dataset becomes the **symbiosis relation space** — 9,900 ordered Dell pairs (and 161,700 triples under FI-006) — queried repeatedly by name/relation. At 9,900 entries the measured scan costs are already ~0.9–1.2 ms/query; there, an index earns its cost. That is a *different index over different data* (relation evidence, not the registry) and should be benchmarked as its own proposal when the symbiosis composition laws pass their held-out test (FI-001's own placement already waits on that evidence).
2. By-name lookup moves onto a per-atom hot path (today it does not; atoms are numeric end-to-end after parsing).
3. A ruling expands the Dell address space by an order of magnitude.

Until one of those holds, FI-001's Phase-4 slot should build **nothing**: the
registry's dict is the index for numbers, and if the by-name scan ever needs
relief, the proportionate fix is a derived name dict inside `registry.py`
itself — not a lattice module, a persisted cache, and a new contract
(SYS-C45) to maintain.

## 4. PHASE-4 BUILD NOTE (if a flip condition ever holds)

Per Q-S1.3, any future index must observe the derivation discipline FI-001's
intake already states (Decision Register, FI-001 entry):

- **Registry wins.** The index is a derived view over `form/mandell/registry.py` (+ `address_space.py`); on any doubt, consumers fall back to the registry. The index can never outrank it and a Dell is never made unreachable by the index.
- **Derived + fingerprinted.** The index carries a provenance header: a fingerprint of its source (the prototype uses sha256 over the canonical sorted `(number, name, manor)` listing — measured cost inside the build figures above), the evidence ids its neighborhoods derive from, and the build pin.
- **Staleness behavior.** Fingerprint mismatch (registry changed since build) → the index refuses and rebuilds or falls back to the registry; corrupt index → same path. Index failure may only ever cost speed, never correctness.
- **Neighborhoods from measured relations only.** Coordinates/neighborhood sets derive from measured relation evidence (family structure, chain co-use counts, symbiosis classifications over a stated threshold, evidence ids on the receipt); unmeasured relations carry an UNKNOWN placement class — still retrievable by address, honestly unplaced by relation. Spatial closeness is never presented as semantic relation.
- **Reproducibility.** Rebuild from scratch reproduces the index bit-for-bit; the benchmark (this script's method: keyed AND scan baselines, medians, stated machine) is re-run at build time and its numbers recorded before any speed claim is made.

## SCOPE AND HONESTY NOTES

- Synthetic registries use generated names/manors; per-item scan costs are representative (same record shape), but real-name lengths differ slightly — the real-registry column is the authoritative one for today's decision, and the synthetic columns exist to locate the flip scale.
- The prototype is deliberately minimal (three standard structures). A more elaborate lattice (spatial coordinates, route graphs) would be *slower* per query than this prototype, not faster — so the prototype is the generous case for FI-001, and it still does not beat the incumbent dict on the hot path.
- `get_dell`'s 560 ns (vs raw `dict.get` 111 ns) is function-call + record-copy + namespace arithmetic — also not an index problem.
