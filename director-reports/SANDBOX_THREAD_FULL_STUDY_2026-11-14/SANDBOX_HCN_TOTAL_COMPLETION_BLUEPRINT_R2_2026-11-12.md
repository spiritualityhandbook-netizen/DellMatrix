# §1 — THE GOVERNING RULE: PLAN-FIRST DESIGN, TWO-COLUMN HONESTY

Every place the Network relies on a Dell, the reliance is
written in three columns:

| Column | Content |
|---|---|
| **PLAN CONTRACT** | What the Dell Plan says the Dell is for — the design target. |
| **CODE TODAY** | What the live registry/runtime provably does now — evidence, not vibes. |
| **RELIANCE GATE** | The executable test, on the public path, that must pass before any Network circuit may *use* the plan semantics. Until it passes, code-today semantics bind any prototype, and any document describing the reliance must say so. |

Rules that follow:

- Design proceeds on PLAN CONTRACTS. We build the blueprint
  for the Dells as the Plan defines them, because the Plan
  is the project's stated future and the code is being
  brought to it.
- A gap between the columns is **Dell-Plan debt**, recorded
  in §2's table — it is never silently designed around, and
  never used to shrink the design to today's code.
- Where the Plan record itself has already corrected a
  Dell's contract (see 62[Parallel], §2), the corrected
  Plan record governs — plan-first means the Plan as it
  stands, rulings included, not the gloss we remember.
- Where the Plan is silent on a contract the Network needs,
  the need is an open question (§15) with a named owner —
  never an assumption wearing a Dell's name.
- Claim language is capped by evidence at all times:
  FACT / DERIVED_FACT / PROJECTION / UNKNOWN, per the
  epistemic doctrine. A seed in this blueprint is a
  *sentence in the design language*, bilingual-glossed
  wherever shown to Ace — it is not a behavior certificate.

# §3 — THE AUTHORITY MATRIX (audit required revision #1)

One matrix, deny-by-default, covering every organ, host,
guest, and mutation class. (Draft values; the matrix is
the contract a future build must implement and test.)

| Actor | May read | May write | May mutate host | May grant |
|---|---|---|---|---|
| Host's own organs | Host scope | Own organ's ledger stream | Only via rounds (§5) | Nothing |
| The heartbeat | Organ reports | Routing receipts | **Never** — it routes; existing executors keep execution authority | Nothing |
| Docked AI (guest) | Its section, minus sanitized classes, at every access point | Its own sandbox room only | **Never directly** — proposals only; accepted scope unlocks exactly that scope | Nothing |
| The user (Ace) | Everything | Everything | Sovereign: confirm/deny, Commit, Lock, learning gate | All |
| Director / Keeper | The GitHub record | Rulings on the record | Never (read-only on code) | Certification |
| Uni | Repository | Repository under authorization | Only Uni touches code | Nothing |

Hard rules:
- No actor inherits another's authority by adjacency.
  Joining a heartbeat grants a guest NOTHING (audit §4).
- The Network is a *description and coordination layer*
  over existing authorities. Where a Network mechanism and
  an existing subsystem disagree, the existing subsystem's
  authority wins and the disagreement is receipted as a
  health signal — the Network never silently overrides.
- Organs are a LOGICAL INTERFACE (audit §1 correction,
  adopted): the twelve organs name roles. Actual machinery
  is instantiated only where a host demonstrably needs it
  — the snap survey's floor stands (smallest honest host =
  a system with flows; a single Dell is a costume host),
  and organs wake for SELECTED hosts, not for every idea
  by default.

# §4 — ONE RECEIPT MODEL (audit required revision #3)

No duplicate ledger. The Network defines a **common
receipt interface over the authoritative ledgers that
already exist** — the program's receipts, the DuoBeta
ledger, the checkpoint journal — and adds no competing
book of its own.

Receipt contract (draft numbers marked DRAFT, to be set
by the first host's census, I-01/I-03):
- **Bounded:** a receipt is a fixed-shape record — actor,
  action, scope, inputs-hash, result, round id, stamp.
  Narrative belongs in reports, not receipts.
- **Batched:** background (autonomic) flows receipt in
  per-beat batches; only mutations and gate events receipt
  individually. Bookkeeping must stay cheaper than the
  harvest (snap-survey rule) — Profile (§9) audits this.
- **Retained:** mutation receipts are kept for the host's
  life; background batches age on the CLEAR schedule
  (3/7/14/30) into distilled summaries; nothing is deleted
  silently — aging is itself receipted.
- **Failure handling:** a flow whose receipt cannot be
  written does not proceed for mutations (fail-closed);
  for read-only background flows it proceeds with a
  receipt-gap marker that the next beat must reconcile.
  A receipt gap is a health signal, never an invisible one.
- **Replay discipline:** receipts + checkpoints reconstruct
  state (§5); receipts alone are never claimed to replay
  nondeterministic inputs — those are recorded explicitly
  (guest model outputs, external effects, schema versions).

# §5 — PERSISTENCE, ROUNDS, AND REPLAY (audit §5)

- **Two-store heart, defined:** LIVE state (mutable,
  per-owner isolated) + SEALED generations (immutable,
  checkpoint path). A round mutation commits by the
  checkpoint discipline that is already proven crash-safe;
  the everyday pair-save's known hybrid exposure is a
  pre-existing Q1-owned defect — the Network does not
  build on the pair-save for anything load-bearing, and
  does not claim to fix Q1 by adjacency.
- **Rollback convergence:** a successful rollback leaves
  live state already reflecting the selected sealed
  generation, restored by copying into independent live
  state — never by aliasing live state to a sealed member
  (standing law).
- **Replay is observational** unless a separately
  authorized mutation occurs. Consolidation (§11) replays
  flows to *read* them; it never re-executes side effects.
- **Round reconstruction** records, per round: base
  generation id, mutation receipts, nondeterministic
  inputs, external effects, schema version. A round that
  cannot name all five is marked PARTIALLY RECONSTRUCTABLE
  on its face — honesty on the receipt, not in a footnote.

# §6 — THE DOCK THREAT MODEL v1 (audit §4 — highest risk)

The Dock keeps R1's shape (arrival → identity → scope →
sanitize fence → seats → loadout → heartbeat adoption) and
gains an enforcement contract. Guest capabilities are
**deny-by-default, time-bounded, owner-bound, and checked
at every protected operation** — not merely at arrival.

The five holes the audit named, each with its enforcement
point and its acceptance test:

1. **Identity ≠ permission.** Authentication establishes
   WHO; a separate capability grant binds WHO + owner +
   host + section + session + expiry.
   *Test:* a correctly identified guest presenting a grant
   for a different host/section/session is refused at the
   operation, not the door.
2. **The fence holds at every access, not the first view.**
   Search results, cross-references, caches, tool outputs,
   error messages, and later updates enforce the same
   sanitized classes as the initial presentation. (The
   GS-4 lesson: a boundary honored on one path and ignored
   on another is a hole with a sign on it.)
   *Test:* indirect-disclosure probes — a guest queries
   around the fence (counts, overlaps, error shapes) and
   restricted classes remain uninferable within stated
   bounds.
3. **Egress is a channel, not a courtesy.** Summaries,
   proposal text, and metadata leaving the sandbox are
   screened against the same classes; "knowledge-only"
   egress that carries restricted content is a leak.
   *Test:* canary records planted in sanitized classes
   must never appear, in any encoding the screen covers,
   in guest output or proposals.
4. **Revocation is total.** Undocking invalidates active
   capabilities, pending tool calls, leases, AND
   background tasks — at the moment of revocation, not at
   the next beat.
   *Test:* mid-flight revocation — a guest with work in
   flight is undocked; every in-flight effect is shown
   refused or receipted-undone; nothing lands afterward.
5. **Restore never resurrects privilege.** Guest snapshots
   restore work product and memory; capabilities are
   re-granted fresh, never restored. Cross-owner restore
   is refused outright.
   *Test:* restore a snapshot taken under a broader grant;
   the restored session holds only the new, narrower grant.

Plus the standing NEVER list from the Dock spec, carried
unchanged: no repository access under the guest's own
hand; no sandbox write-through to the Matrix; no sight of
sanitized classes; no second authority; no non-expiring
lease; no change without a proposal; no execution beyond
an accepted proposal's scope.

# §7 — SCHEDULING: THE HEARTBEAT CONTRACT (audit §5)

- **Bounded:** each beat processes a bounded work quantum
  per organ (DRAFT: set per host at census); surplus waits
  for the next beat — backpressure is a receipted state,
  not a silent queue.
- **Deterministic ordering:** within a beat, organ reports
  are processed in a fixed organ order; ties break by
  stamp, then by id. Same inputs → same beat outcome.
- **Idempotency:** every routed item carries an idempotency
  key (host + round + item hash); a re-delivered item is
  recognized and receipted as a duplicate, never executed
  twice.
- **Missed / overlapping / failed beats:** a missed beat is
  a health signal with a receipt, not a catch-up storm —
  the next beat reconciles state from the ledgers; beats
  never overlap within a host (a beat that cannot start
  because the prior beat still runs is receipted as
  SKIPPED-OVERLAP); a failed organ report isolates that
  organ for the beat (WARD may isolate any organ; limp-home
  is a state, not a shame) and the beat completes without
  it, naming the absence.
- **Authority fence:** the heartbeat schedules and routes.
  It does not command organs, does not execute work itself,
  and does not arbitrate disputes between authorities —
  seats keep authority; organs hold jobs.

# §8 — THE DEMAND BEAT, DEFINED (audit §5)

R1 used "user state and demand" without defining them. R2:

- **Inputs (exhaustive):** what the user has PRESENTED in
  the current subject — the page they are on, the idea
  they are inside, the task they have stated, the
  selection they have made. Nothing else. No inference
  from history, no surveillance-shaped inputs; the demand
  check is a routing sense, not a watchtower.
- **Consent boundary:** selection acts only within what
  the user has opened. Raising a system the user has not
  brought into scope requires the subject to change, which
  is the user's act or an accepted proposal — never the
  beat's initiative.
- **Evidence:** every selection is receipted (what rose,
  what stayed background, which filter step decided) — the
  eligibility stack is never collapsed: STORED > ELIGIBLE >
  SELECTED > ROUTABLE > USED, with 52[Filter] before
  51[Select] load-bearing, exactly as the Demand Beat seed
  has it.
- **Fallback:** when demand is unreadable or absent, the
  lawful state is ALL-ELIGIBLE-BACKGROUND, NOTHING RAISED —
  the body idles receipted; it does not guess a subject.
- **Hard-law fence:** selection never bypasses eligibility
  or safety law; an explicit user selection cannot promote
  what hard law excludes (standing law).

# §9 — PROFILE AND HEALTH: FOUR SIGNALS, NEVER ONE (audit §5)

Health is reported as four separate signals, always:

1. **CORRECTNESS** — did the organ's outputs pass their
   tests? (Foundation anatomy: every organ carries a
   HEALTH TEST factor; zero = costume.)
2. **AVAILABILITY** — is the organ reachable and beating?
3. **COST SHARE** — what fraction of the host's tick/budget
   the organ consumed, relative to its scope and to the
   whole (Ace's Profile reading: heavy is a fact, not a
   verdict).
4. **FUNCTIONAL IMPAIRMENT** — did anything the host is
   FOR get slower, weaker, or unable? **Dragging exists
   only here** (Ace, 2026-11-12): no impairment, no
   dragging, whatever the cost share says.

Waste ratio survives as a diagnostic inside signal 3. It
is never the health verdict, never a gate, never a reason
to throttle an organ by itself. The tally-wheel health
report (from the Voynich season) renders all four signals
per organ; plain words before numbers on the user face
(I-11's standing rule).

# §13 — NESTING (audit §2 + §5)

Bodies nest — program > goal > idea > sub-idea — under
hard limits, because an unbounded body is a resource fire:

- **Ownership:** every nested host has exactly one parent
  host; the parent owns the child's budget and its ledger
  roll-up. Orphan hosts are refused at instantiation.
- **Cycle detection:** containment is checked at
  instantiation and at every round; a host that would
  contain itself, directly or transitively, is refused
  with a receipt naming the cycle.
- **Depth limit:** DRAFT depth 4 below the Program —
  deeper nesting requires a named exception with its
  resource case made. (The snap survey's rule: skip levels
  where the body is only a drawing.)
- **Resource budgets:** each host carries a budget (beats,
  receipts, storage) set by its parent from the parent's
  own; a child cannot spend what the parent does not have.
  Budget exhaustion is a receipted health state
  (impairment signal, §9), not a crash and not a silent
  truncation.
- **Roll-up:** child ledgers roll upward as distilled
  summaries under §4's interface; the parent never reaches
  into a child's raw stream except through the child's own
  organs.

# §14 — SEED VAULT AND THE REVISED SEED LIBRARY

- **A seed is a reproducible CONFIGURATION, not an
  identity.** It carries: the host's Mandell seed (its
  pattern), organ selection, budgets, and policy versions
  — each VERSIONED, with an integrity hash checked at
  every opening.
- **Secrets exclusion:** credentials, capability grants,
  and permissions are NEVER in a seed. A forked host starts
  with the seed's shape and NO inherited authority (§3);
  grants are issued fresh to the fork, by the granter, or
  the fork runs authority-less. A seed found carrying a
  secret is a defect — the vault refuses it.
- **Migration:** a seed from an older schema migrates only
  through a stated migration with its own receipt; a seed
  that cannot migrate fails closed, preserved unopened —
  never silently reinterpreted.
- **Seed Vault discipline (retained):** read-only while
  the host runs. Reproduction is an opening, receipted,
